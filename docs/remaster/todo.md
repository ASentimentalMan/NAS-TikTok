## 2. 模块边界与目标目录

采用**模块化单体（modular monolith）**：一个主要 Go 服务进程，按业务边界拆包；无需引入微服务、消息队列、数据库或 Redis 作为默认依赖。保持模块独立可测，避免将业务堆在 `main.go`、`router.go` 或一个巨大的 `utils.go`。

**建议最终 Go 代码根目录为 `backend/`**，让迁移期间可以与旧 `server/` 并存并独立验证；所有调用生产后端的构建/部署环节切换成功后，旧 NestJS `server/` 不再进入最终运行路径。旧实现由 Git 历史追溯；不要为了保留旧代码而让生产容器常驻两套 API。若当前仓库结构对命名另有合理要求，可作等价调整并说明映射。

下面是逻辑包结构与**职责约束**，不要求机械拆成每项一个文件：

```text
backend/
  go.mod
  cmd/nas-tiktok/main.go           # 唯一程序组合、启动入口
  internal/
    app/                           # 生命周期、依赖组装、优雅关闭
    config/                        # 环境配置解析、类型化校验
    transport/httpapi/             # 路由、请求/响应 DTO、中间件衔接、错误响应
    access/                        # 客户端 IP 识别、IPv4/IPv6 CIDR、访问策略
    auth/                          # 单账号凭据验证、登录业务
    captcha/                       # 数学 SVG 验证码、TTL、一次性消费与存储接口
    session/                       # Token 签发/验证、身份上下文、会话策略
    media/
      catalog/                     # 根目录、扩展名集合、目录遍历、媒体路径标识
      sampling/                    # 水库抽样（与文件遍历解耦）
      streaming/                   # 文件开放、HTTP GET/HEAD/Range、MIME、响应头
    web/                           # Vue dist 和 env.js、SPA 静态资源托管
    observability/                 # 日志/错误脱敏与请求观测
  ..._test.go                      # 测试与各包就近放置
```

**跨包依赖约束：**

- `cmd` / `app` 负责构造具体实现和注入依赖；业务包不反向依赖入口。
- `httpapi` 处理 HTTP 解析、身份上下文传递、状态码及 JSON；**不在路由处理函数内写目录遍历、密码比对、文件流协议算法**。
- `auth` 处理账号校验；`captcha` 处理答案生成/存储/校验；`session` 处理身份令牌；三者通过小接口组合，不互相形成循环依赖。
- `access` 仅处理网络来源与 IP 策略，和用户登录状态分离。
- `catalog` 知道目录、路径和媒体扩展名；`sampling` 实现对候选项的抽样，不负责读取环境变量或 HTTP 写响应；`streaming` 负责文件传输协议而不承担登录业务。
- `web` 只处理前端产物与运行时配置，不包含媒体文件业务。
- `config` 不引用业务模块；`observability` 不包含领域规则。
- 接口放在**实际使用侧**，尽量少、尽量小。不要为每个简单函数套复杂仓储层或泛型抽象。
- 可按文件数量适度合并包，**但不可将认证、目录扫描、HTTP Range、部署配置混为单一模块**。

## 3. 逐模块行为契约

以下条目将 `function.md` 的既有行为映射到新实现中。须覆盖所有 14 个功能领域，不因重命名遗漏职责。

### M01 — Application Runtime

- 单入口启动、读取配置、构造组件、创建 HTTP Server、注册路由与中间件、输出启动信息、接收退出信号并优雅关闭。
- 以 Go 进程的并发处理能力提供 I/O 服务；不继续使用 PM2 Cluster。
- 支持普通 HTTP 和按配置启用的 HTTPS；维持生产环境 HTTP/2 能力。实际证书路径、监听地址、端口从配置读取。
- 对启动失败、监听失败、请求中断、进程退出有明确日志及退出码。

### M02 — Configuration

- 覆盖旧配置：`APP_NAME`、`APP_URL_PREFIX`、`VITE_API_URL`、`VITE_API_PORT`、`ACCOUNT`、`PASSWORD`、`JWT_SECRET`、`JWT_EXPIRE`、`ALLOWED_IPS`、`ALLOW_IPv6`、`SSL`；理解旧 `.env` 开发/生产语义。
- 新配置模型应把**服务监听**、**客户端可见 API 地址**、**前端部署路径**、**媒体根目录**与**TLS 证书路径**明确区分；兼顾原有变量兼容性，新增变量集中定义。
- 使用类型化配置、启动期校验和安全默认值；敏感值不写日志。提供 `env.example`，真实凭据只在部署时注入。
- 明确配置缺失、空白、布尔、整数、CIDR、端口和 JWT 过期时间的处理；生产/开发模式行为一致可预期。

### M03 — HTTP Infrastructure

- 保留旧业务 API（见第 4 节）和静态服务路由。
- 一处完成路由注册、统一错误响应、HTTP 方法处理、请求上下文、CORS、内容类型、请求体限制及中间件组合。
- 保留接口级别的业务错误语义：验证码错误、账号密码错误、未登录、登录过期、IP 禁止访问、文件不存在、无效范围等。
- 将**公开认证例外**与**IP 限制**作为不同判定维度。

### M04 — Network Access Control

- 保留可配置 IP 白名单、IPv4/CIDR、IPv6 与回环地址的现有用途。
- 明确 `ALLOW_IPv6` 的监听含义及实际访问授权规则；按配置执行 IPv4/IPv6 CIDR 判断，不将监听开关直接等同于授权。
- 正确区分直连、Docker host、bridge、可信反向代理场景中的客户端地址；**不盲信用户可伪造的转发 Header**。
- 包含单测覆盖回环地址、IPv4/IPv6、映射地址、网段边界和非法配置。

### M05 — Captcha

- `GET /api/captcha`：继续提供数学表达式 SVG，返回验证码标识和前端可展示的 `data:image/svg+xml;base64,...`。
- 保留验证码有效期约 5 分钟、答案核对、校验后消费的语义。
- 在单 Go 进程下可采用受控的进程内存存储；封装小接口，使多实例化时能替换存储，**不将 Redis 引为默认必需项**。
- 验证码标识使用适合认证场景的安全随机数；管理过期项与并发消费；配合登录/验证码获取限流。
- 保留人类可输入的数学答案以及当前前端提交的 `codeId`/`code` 字段。

### M06 — Account Authentication

- `POST /api/logIn`：接收 `account`、`password`、`codeId`、`code`，在验证码校验后验证环境配置的一组账号密码。
- 维持**单账户、无数据库依赖**的产品模型。
- 成功后建立已认证会话并返回前端可处理的成功响应；错误有稳定状态码/错误格式。
- 不需要添加注册、找回密码、多用户、RBAC 等新业务。
- 对登录和验证码请求有合理的请求频率控制，不写入明文密码日志。

### M07 — JWT & Session

- 保留令牌/会话的签发、有效期、验证、登录保护、公开路径、身份上下文功能；区分会话标识与业务账号。
- 不继续把**长期登录 JWT**拼接到图片/视频 URL 上。优先在同源部署下使用浏览器支持的 `HttpOnly` 会话 Cookie（HTTPS 下 `Secure`，明确 `SameSite`、CSRF/Origin 策略）。
- 原前端从 `localStorage.token` 读取 JWT、媒体 URL 追加 `?auth=`；必须同步完成相关前端适配（见第 5 节），并验证 iOS Safari `<video>`/`<img>` 的实际媒体加载行为。
- 若实际同源/跨源部署限制使 Cookie 方案不可行，允许采用**短生命周期、仅限单媒体的授权方式**，须写明原因、令牌范围、生命周期与隐私影响；不得默默保留通用长期 JWT URL 模式。
- 让会话过期、登出/失效（若引入对应接口）、密码或密钥变更后的会话行为明确；会话功能复杂度须与单账号产品相称。
- 原有 Header/IP 绑定属于旧行为事实；以可信、可测试的会话行为取代易随协议或网络变化而变化的偶然条件，不必复刻非必要的 Header 逐项相等比较。

### M08 — Media Storage

- 继续读取 NAS 文件系统，不复制整个媒体库、不引入上传/删除/转码功能。
- 保留媒体根目录可配置（旧开发 `server/statics`、容器 `/workspace/statics`），并支持媒体目录的**只读**挂载。
- 视频扩展名：`.mp4 .webm .mov .ogv .ogg`。
- 图片扩展名：`.jpg .jpeg .heic .heif .avif .webp .png .gif .apng .bmp`。
- 大小写不敏感；保留 MIME 识别和未知格式回退的响应语义。
- 文件路径始终以媒体根目录为访问边界，包含合法多级目录、特殊字符/Unicode、符号链接行为与路径编码处理的明确定义。

### M09 — Media Discovery & Sampling

- `GET /api/list?type=image|video`：根据请求类型递归发现符合扩展名的文件；跳过目录名 `@eaDir`；保持最多 10 个结果、随机抽样、响应 `{"data":["媒体URL",...]}` 的语义。
- 原实现采用单遍水库抽样，不依赖数据库；在 Go 实现中仍须保证样本随机性，并控制扫描内存。
- 扫描与抽样为可独立测试的步骤；目录读取失败、空目录、深层目录、大目录均有定义。
- 控制并发重复扫描；不要增加隐藏的无限后台索引任务。可在明确内存/时效语义下做轻量索引或去重优化，但不得改变“随机浏览 NAS 内容”这一业务目标。
- 媒体列表的 URL 要在浏览器与服务部署的协议、地址、子路径下正确工作，不能依赖暴露会话 JWT 的查询参数。

### M10 — Media Streaming

- 支持媒体文件 `GET` 和 `HEAD`，正确处理完整响应、标准 HTTP Range、206、416、`Content-Type`、`Content-Length`、`Content-Range`、`Accept-Ranges`、`Content-Disposition`。
- 允许浏览器读取大文件、拖动视频进度条、在 iOS/Safari 上发出 Range 请求；采用流式 I/O，不将整个媒体载入内存。
- 对 URL 解码、根目录边界、绝对路径、`..`、符号链接、目录/非普通文件进行严格的文件打开约束；**API 输入不能读取媒体根目录之外的文件**。
- 对客户端主动断开、文件不存在、读取失败、范围异常进行可靠处理；所有资源在响应结束或取消后释放。
- 私人媒体缓存与会话语义匹配，不允许公开共享缓存意外保留私人内容。必要时可利用 Go 标准库 `http.ServeContent` 等成熟文件传输行为，仍须单独处理授权及文件根目录约束。
- 支持旧媒体文件名和路径中包含空格、中文、括号等字符。

### M11 — Static Web Hosting

- Go 后端继续可独立托管 Vue 构建后的 `client/dist`。
- 保留静态资源、SPA 前端路由回退和前端运行时配置 `env.js`；正确区分静态文件请求与 `/api` 请求，避免 API 404 被错误地返回 HTML。
- 前端运行时必须能取得服务地址/端口或等价的同源 API 基址；兼顾本地开发、生产 HTTP/HTTPS、配置的部署子路径。
- `env.js` 的内容只包括可公开的前端配置，不包含账户密码、JWT 密钥、证书等秘密。
- 不为了重写后端而重写 Vue 路由、组件或 PWA 视觉交互。

### M12 — Error Handling & Logging

- 保留业务错误与 HTTP 失败的可识别语义；错误响应格式统一，前端能据此区分未登录、验证码错误、账号密码错误、404、网络中断。
- 日志记录必要的请求信息和内部错误上下文，不记录账户密码、JWT、Cookie 或 URL 内的秘密。
- 对预期业务错误和内部异常采用可区分的状态与日志级别；不会向客户端直接暴露系统文件路径或密钥值。

### M13 — Common Types & Utilities

- 旧 `generateUUID`、IPv4 数值转换、`isAllowedIPs`、JWT 接口、`@Public`、`@JWT` 的**用途**分别落到相关模块；不需要机械照搬 NestJS 装饰器或 TS 类型。
- 共享类型应体现 Go 业务数据和接口约定；普通工具留在实际领域包，不创建吸收所有代码的通用大包。

### M14 — Build & Deployment

- 最终生产 Docker 镜像通过多阶段构建得到 Vue 静态产物和 Go 二进制；容器 API 服务由 Go 进程运行，而非 PM2。
- 保留 TLS 证书挂载、NAS 媒体目录挂载、可配置监听端口、Docker host/bridge 部署说明、镜像构建、镜像导入/导出等现有运营能力。
- `build.sh` 如继续保留，其构建源码、镜像版本、启动参数、分支/Commit 选择应与新 Go 后端一致；不能默默从 `main` 构建旧代码。
- 镜像不携带实际 `.env` 秘密；以运行时配置提供账户、密码与签名材料。使用可复现依赖和合适的非特权运行身份。
- 清理生产路径中不再使用的 Node/PM2 后端依赖、脚本和配置，同时保持前端 Node 构建链正常。

## 4. HTTP API 契约与兼容性

**以端用户功能和前端实际消费行为为优先兼容目标**。原后端业务路由有四个：

| 方法 | 路径 | 输入 | 原业务输出/效果 |
|---|---|---|---|
| GET | `/api/captcha` | 无 | `{id, data}`，SVG Data URI |
| POST | `/api/logIn` | `{account,password,codeId,code}` | 登录成功，旧版 `{token}` |
| GET | `/api/list?type=image\|video` | `type` | `{data: string[]}`，最多 10 个媒体 URL |
| GET / HEAD | `/api/stream/...` | 文件路径、可选 `Range` | 媒体流、206/416、相应响应头 |

契约边界：

1. **保留路由路径及业务字段**，如确需改变登录成功响应，前后端须同一改动中同步，并在文档记录“原 → 新”契约。`{token}` 不必作为最终不可变 API，不能为了强行保持它而继续把长期令牌暴露给 JavaScript 或 URL。
2. `/api/list` 仍返回浏览器可使用的媒体 URL 字符串，而不是未经约定改成分页对象/媒体数据库记录；错误响应可统一，但应保持前端已使用的消息展示能力。
3. 验证媒体 URL 的相对/绝对地址、IPv6 地址、协议、端口和部署子路径组合；明确 `/api` 与 `APP_URL_PREFIX` 的关系，避免把旧代码中的配置拼接偶然性变成永久契约。
4. API 鉴权、IP 访问控制、公开登录/验证码的例外，必须在集成测试中分别验证。
5. 正确处理 `HEAD`、`OPTIONS`、`GET`、`POST`；登录预检和 Cookie 凭据策略与实际部署来源一致。
6. 对 `GET /api/list` 的非法类型给出明确定义及测试，不依赖 TS 联合类型在运行时自动阻止非法输入。
7. SPA 页面路由与 API 路由不能互相覆盖。

## 5. 前端必要适配（不重写界面）

审查并只修改与后端迁移有关的实际调用点，至少包括：

- `client/src/apis/index.ts`：登录、验证码、图片/视频列表和 401 处理、API 基址与认证携带方式。
- `client/src/views/login/index.vue`：登录成功流程、记住账号的持久化内容、原 `savedLogin` 数据兼容清理。
- `client/src/components/VideoPlayer.vue`：`<video><source>` 的授权媒体 URL、`HEAD` 错误检测、Range、播放/快进。
- `client/src/components/ImagePlayer.vue`：`<img>` 的授权媒体 URL和加载失败处理。
- `client/src/router/guard.router.ts`：路由鉴权不再仅依赖 `localStorage.token` 的存在性。
- `client/public/env.js`、`client/index.html`、`client/vite.config.ts`：运行时 API 配置、脚本加载顺序、开发代理及部署路径。

其他播放器的触摸、随机跳转、速度、缩放、旋转、自动播放、标签切换与 PWA 行为作为**回归保护范围**；迁移必要性之外不要改写。

**安全认证方式发生变化时，前端和后端必须作为一个可运行切片同时提交**，不允许出现“新后端只支持 Cookie，但前端仍靠 `?auth=`”的中间完成态。若部署支持本地 HTTP 与 HTTPS，明确开发 Cookie 和生产 Cookie 的不同条件。旧 localStorage 内的密码和会话数据应被安全迁移/清除。

## 6. 审计报告纳入方式

必须逐项读取 `docs/remaster/audit.md` 的 `AUDIT-001` 至 `AUDIT-036` 以及 `VERIFY-*`、`TEST-*` 条目，并逐个建立追踪记录。**不把旧审计的优先级、影响范围或复现状态视为无需验证的结论**；标记为适用于新 Go 实现的风险、迁移自然消除的旧技术栈问题、已验证不成立或需环境验证的问题。

重要安全/行为主题：

- 媒体根目录边界及符号链接（AUDIT-001）。
- 配置文件与密钥泄露、密钥轮换归属（002、003、014）。
- IPv4/IPv6 白名单和客户端 IP 来源（004、018）。
- 媒体 URL 的登录令牌、私人内容缓存与日志（005、006、019）。
- 多进程验证码与状态存储（007；新 Go 单进程下重新确认）。
- CORS/预检与可信 Origin（008）。
- 浏览器密码持久化（009）。
- HTTP Range 和文件流错误（010、011、026）。
- 登录限流、会话有效期/失效（012、015、016、017）。
- Docker 网络、镜像、脚本、可复现构建（013、033、034）。
- 扫描成本、列表重复请求、播放器状态和生命周期（020 至 029；只处理迁移需要或明确的功能回归问题）。
- 依赖风险、CI、测试、文档、许可证（030 至 036）。

处理状态建议：

`FIXED` / `MITIGATED_BY_REPLACEMENT` / `NOT_REPRODUCED` / `PARTIAL` / `BLOCKED` / `NOT_RUN`。

**不得在代码、日志、报告中复制真实 `.env` 秘密。** Codex 可清理当前跟踪文件与镜像配方，**不能替所有者实际更改外部部署的密码、签名密钥或直接重写仓库历史**。需由人操作的密钥轮换单独列明。

## 7. 分阶段执行（每阶段必须可验证）

### Phase 0 — 基线冻结与映射

1. 查看 `git status`、分支、当前 `HEAD`，阅读两份文档和全部后端源码与前端 API 调用点。
2. 整理“旧文件/函数 → 新 Go 包/函数 → API 或 UI 使用方”的映射，覆盖 M01–M14。
3. 定义旧 API 及改动后的认证契约、环境变量映射、部署模式与回归测试清单。
4. 标注 `audit.md` 需要验证的条目，不提前宣称已经消除。

### Phase 1 — Go 可运行骨架

1. 创建 `backend/` Go 模块、`cmd`、`app`、`config`、HTTP Router、错误响应、日志与健康检查。
2. 增加最小的 Go 单元测试、配置测试和启动验证。
3. 验证 Go 服务在本地能够启动、监听并正确退出。

### Phase 2 — 访问控制与身份

1. 实现 `access`、`captcha`、`auth`、`session` 的独立业务逻辑与接口适配。
2. 集成 `/api/captcha`、`/api/logIn`，以及受保护 API 的身份与来源判定。
3. 落实安全令牌传输和必要的浏览器认证适配。
4. 测试验证码一次性消费、TTL、登录失败、IP/CIDR、会话过期、非法 JWT、限流、并发场景。

### Phase 3 — 媒体发现与流式传输

1. 实现媒体类型、目录发现、`@eaDir` 规则与水库抽样。
2. 实现带安全根目录边界的文件打开、GET/HEAD/Range 和 MIME 响应。
3. 联通 `/api/list`、`/api/stream/...`，保持返回格式和支持的媒体类型。
4. 用真实临时文件/测试目录进行路径、特殊字符、符号链接、空目录、大文件、206/416、客户端取消与并发测试。

### Phase 4 — Vue 对接与端到端闭环

1. 完成登录、验证码、媒体列表、视频、图片、过期登录状态的前后端贯通。
2. 完成静态前端服务及 `env.js` 机制，校验 HTTP/HTTPS、前端子路径与 API 基址。
3. 验证主要交互：滑动、视频随机跳转、倍速、旋转、静音、图片缩放/旋转/自动播放、PWA 基本入口。
4. 前端不保留旧长期 JWT URL 认证路径，不持久化明文密码。

### Phase 5 — Docker 与 NAS 交付

1. 构建含 Vue dist + Go 二进制的最终镜像，运行时不启动 NestJS/PM2。
2. 更新 `build.sh`（若保留）和部署文档，说明 host/bridge、端口、TLS、媒体只读目录、证书、环境变量、arm64/amd64。
3. 验证新镜像内没有真实凭据，容器可启动并能从挂载目录返回媒体。
4. 清理生产路径中的旧后端依赖，保留 Git 提交历史用于追溯。

### Phase 6 — 回归、质量门禁与交付

1. 运行测试、Race 检查（可用平台）、静态检查、Go 编译、Vue 类型检查与构建、Docker 构建，以及适用的依赖漏洞/密钥扫描。
2. 建立 CI 检查：Go 测试与构建、前端检查和构建、依赖/敏感信息检查；**不得把环境没有执行过的检查写成 PASS**。
3. 更新 README 与 `docs/remaster/` 相关说明，输出审计项处置表、兼容性变更说明与测试证据。
4. 确保部署的生产入口只指向 Go 后端。

按以上阶段组织提交与验证；**无需为每一步创建独立服务或仓库**。如果环境无法完成某类端到端验证，先实现可自动化的部分，再明确记录人工验证步骤和未完成证据。

## 10. 交付报告格式

在最终答复和仓库内的 `docs/remaster/result.md`（如有必要也可命名 `report.md`）使用以下结构：

1. **基线**：仓库、分支、起止 Commit、范围。
2. **模块映射**：M01–M14 的旧代码职责 → 新 Go 包/入口，以及未迁移项原因。
3. **API/配置对照**：旧路径/字段与新路径/字段、认证和部署契约变更。
4. **变更文件概览**：Go、Vue、Docker、脚本、文档和测试。
5. **审计追踪表**：AUDIT-001～036 的状态、证据、残留限制；另列 VERIFY 项。
6. **执行验证**：实际执行的命令、结果、测试用例数或构建产物；失败/未运行项目。
7. **兼容性**：HTTP/HTTPS、IPv4/IPv6、NAS 文件目录、Docker host/bridge、Safari/iOS/PWA（未测明确标注）。
8. **需要人工操作**：环境变量、证书、部署切换、已经暴露的账号与密钥轮换。
9. **剩余风险和限制**：用可复现事实描述，而非泛泛声明。

## 11. 执行原则

- **从代码事实出发，不迷信旧实现细节，也不盲目照搬审计结论。**
- **优先功能等价和安全边界，其次性能优化，再次美化代码。**
- 以**能单独测试的业务职责**为模块拆分单位，而不是每个函数一个 package；避免形成一坨代码，也避免无意义的抽象层。
- 凡是修改认证传输、前端 API 格式或部署约定，必须同步修改依赖它的所有调用方、测试和文档。
- 不修改真实 NAS 媒体，不执行生产部署，不擅自推送/合并、不重写 Git 历史、不处理外部账户的实际密钥轮换。
- 遇到环境限制，尽最大可能完成可执行的当前工作，再准确列出限制；不要只输出计划而停止实现。

**最终目标：保留 NAS-TikTok 的现有产品体验，将后端从 NestJS/PM2 重写为结构清晰、可独立测试、可部署且在 NAS 上稳定运行的 Go 模块化单体，并以真实测试证明迁移完整性。**
