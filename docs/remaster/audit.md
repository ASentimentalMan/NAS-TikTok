1. 文件流接口缺少路径边界限制。

当前分支不建议在未经修复和验证的情况下，
直接用于存有敏感私人媒体的公网可达 NAS。

AUDIT-001：媒体文件接口存在目录穿越风险
------------------------------------------------------------

严重程度：P0
状态：[确认] 不安全的文件路径拼接
利用可达性：[待验证]

涉及文件：

server/src/modules/stream/stream.controller.ts
L13-L20

server/src/modules/stream/stream.service.ts
L112-L126

问题：

stream.controller.ts 使用通配符路由接收文件路径。

stream.service.ts 中：

const decodedPath = decodeURIComponent(filePath);
const path = join(this.workDir, decodedPath);

没有限制解析后的路径必须位于 workDir 内。

Node.js 的 path.join() 会处理 "../" 路径段。

例如：

join(
  "/workspace/statics",
  "../server/.env.development"
)

结果会指向：

/workspace/server/.env.development

这是明确的文件系统边界缺失。

如果 HTTP 路由允许编码后的目录穿越路径进入该函数，
拥有有效访问令牌的请求可能读取媒体目录之外的文件。

在当前 Docker 目录结构下，潜在目标包括：

- 服务端环境配置
- JWT 签名密钥
- 证书和私钥
- 服务端源码及其他文件
- 容器中可被当前进程读取的敏感文件

另一个问题是没有处理媒体目录中的符号链接。

即使仅使用普通文件名，
指向目录外部的符号链接也可能突破预期边界。

必须修复：

1. 严格限制文件访问根目录。
2. 规范化并验证客户端提供的路径。
3. 使用 path.resolve() 建立规范化路径。
4. 使用 realpath() 检查实际文件位置。
5. 确保目标始终位于合法媒体目录内部。
6. 正确处理符号链接。
7. 拒绝绝对路径。
8. 拒绝非法路径编码。
9. 拒绝非普通文件。
10. 只允许明确支持的媒体文件类型。
11. 不应仅检查字符串是否以目录名称开头。
12. 防范检查与打开文件之间的竞态条件。
13. 保留正常多级媒体目录浏览功能。

验收标准：

- 正常媒体文件可以访问。
- 多级目录中的媒体可以访问。
- ".." 路径被拒绝。
- URL 编码的目录穿越被拒绝。
- 双重编码场景被测试。
- 绝对路径被拒绝。
- 指向根目录外的符号链接被拒绝。
- 无法读取服务器环境文件。
- 无法读取 TLS 私钥。
- 非法请求不会导致进程异常退出。

特别要求：

必须增加 HTTP 集成测试验证路由实际解码行为，
而不只是测试 path.resolve()。

这不是安全的 JWT 密钥。

如果该值进入 JWT 签名配置，

可能导致使用可预测密钥签发令牌。

4. 禁止 "undefined"、"null" 和默认示例值。
5. 强制足够的随机密钥强度。
6. JWT_EXPIRE 必须为有效正整数。
7. 禁止 NaN、负数和异常过期时间。
8. 配置无效时立即阻止应用启动。
9. 不得将密钥内容打印到日志。
10. 对现存密钥提供安全轮换策略。

验收标准：

- 缺少密钥时启动失败。
- 空密钥时启动失败。
- 弱密钥时启动失败。
- 正确配置时签名及验证成功。
- 过期令牌被拒绝。
- 篡改的令牌被拒绝。
- 旧密钥轮换后的处理符合预期。

AUDIT-007：PM2 多进程验证码缓存不共享
------------------------------------------------------------

严重程度：P1
状态：[确认] 架构不兼容

涉及文件：

server/src/app.module.ts
L21

server/src/modules/auth/code.service.ts
L7-L52

server/ecosystem.config.js
L6-L8

当前结构：

CacheModule.register({ isGlobal: true })

同时 PM2 使用：

exec_mode: 'cluster'
instances: 'max'

默认缓存没有配置进程间共享存储。

多个 Node.js Worker 各自维护独立内存。

可能发生：

验证码由 Worker A 创建。

登录请求被 Worker B 处理。

Worker B 无法找到 Worker A 创建的验证码。

结果：

正确验证码也可能被提示错误。

必须修复：

方案 A：

使用 Redis 等共享缓存，并明确 TTL。

方案 B：

避免依赖跨进程内存状态，
设计无状态的验证码签名方案。

方案 C：

如果坚持单进程内存缓存，
应明确使用单实例模式并记录其限制。

建议优先考虑方案 A 或 B。

还需要：

- 原子性消费验证码
- 防止重复提交
- 正确的验证码过期处理
- 限制验证码数量
- 限制登录尝试次数

验收标准：

在多个 Worker 之间随机分发请求，
验证码仍能稳定完成校验。
